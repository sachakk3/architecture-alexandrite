# Архитектурные и инфраструктурные проблемы

    - Единые точки отказа и отсутствие горизонтального масштабирования: Каждое приложение (Shop, CRM, MES) развернуто ровно в одном инстансе, а базы данных работают в единственном инстансе на чтение и запись. Падение любого узла полностью парализует обработку заказов.
    - Расчет стоимости по 3D-моделям (от 2–3 до 30 минут) выполняется на MES, при росте входящих заказов (B2C + B2B API) потоки/воркеры MES могут вызвать деградацию и зависание всей MES системы.
    - Отсутствие реплик на чтение и кэширования: Пагинация и фильтры в MES не решают проблему, так как сложные выборки («самые новые заказы в определенных статусах») идут напрямую в мастер-БД.

# Бизнес-логика и межсервисная интеграция

    - Если сообщение в RabbitMQ теряется, падает в Dead Letter Queue или не подтверждается, заказ зависает в промежуточном состоянии и «теряется» для менеджеров и клиентов.
    - Непрозрачный жизненный цикл заказа и отсутствие трекинга зависаний: Нет мониторинга нахождения заказа в статусах (например, PRICE_CALCULATED -> MANUFACTURING_APPROVED). Если заказ не взят оператором или застрял в очереди, об этом узнают только по жалобам клиентов через недели.
    - Отсутствие Rate Limiting / Quotas на публичном API: B2B-партнеры могут отправлять тяжелые 3D-модели, создавая нагрузку и вытесняя обычных розничных клиентов.

# Процессы, команда и CI/CD

    - В CI/CD не хватает интеграционных тестов
    - E2E тесты запускаются вручную. Один manual QA тестирует все системы вручную перед каждым релизом. По мере роста кодовой базы задержки релизов превышают месяц, блокируя хотфиксы и оперативные доработки.
    - Не предусмотрено нагрузочное тестирование
    - На фронтенде MES работоает инженер с частичным знанием React
    - Недостаток сквозной наблюдаемости. Отсутствие корреляционных идентификаторов (TraceId / CorrelationId) между Магазином, RabbitMQ, MES и CRM не позволяет быстро выяснить, на каком этапе теряются заказы.

# Инициативы, которые необходимы для устранения нежелательных ситуаций в порядке приоритета

    1. Внедрить мониторинг зависаний заказа
      - Описание: Внедрение сквозного CorrelationId через все системы и очереди RabbitMQ, настройка алертинга на «зависшие» заказы (если заказ находится в статусе дольше $X$ часов/дней) и интеграция Dead Letter Queue (DLQ) для исключения потери сообщений.
      - Обоснование: Позволит оперативно найти уже потерянные заказы и оперативно устранять проблему зависших заказов в будущем.
    2. Вынос и оптимизация запросов дашборда MES
      - Описание: Добавление составных индексов в БД MES под фильтры операторов (status + created_at), оптимизация SQL-запроса получения списка заказов, подключение Read-реплики или кэширования для первой страницы.
      - Обоснование: Быстро снимает блокировки с БД MES и возвращает операторам возможность нормально работать без зависания интерфейса.
    3. Запуск приложений на нескольких инстансах, добавление балансировщика нагрузки.
      - Описание: Развертывание каждого сервиса (Shop, CRM, MES) минимум в двух экземплярах за балансировщиком нагрузки с переходом
      - Обоснование: Устраняет единую точку отказа (SPOF). Система перестанет падать целиком при сбое одного сервера и сможет выдерживать наплывы B2B/B2C трафика.
    4. Репликация и кеширование баз данных.
      - Описание: Внедрение Read-реплик для разделения потоков чтения/записи (CQRS) и L2-кэша (Redis) для частых запросов
      - Разблокирует мастер-базу для быстрых транзакций. Тяжелые дашборды операторов перестанут вешать систему, так как будут читать данные из реплики, а шардирование на текущих объемах избыточно.
    5. Вынесение расчета стоимости по 3D-моделям в отдельный сервис
      - Описание: Изоляция тяжелого CPU-bound алгоритма расчета стоимости из монолита MES в отдельный фоновый сервис воркеров с горизонтальным автоскейлингом.
      - Обоснование: Модели, считающиеся по 30 минут, больше не будут блокировать потоки веб-сервера MES и базу данных.
    6. Внедрить Rate Limiting / Quotas для равномерного распределения нагрузки между пользователями API
      - Описание: Установка лимитов на количество запросов в минуту от B2B-партнеров, предварительная валидация размера файлов и базовой сложности 3D-моделей перед постановкой в очередь.
      - Обоснование: Защищает контур от неконтролируемого DoS со стороны внешних интеграторов.

# Целевая архитектура через полгода

    1. Через полгода система должна иметь дашборд Prometheus/Grafana с мониторингом задержек на каждом статусе и отслеживанием сквозного SLA
    2. Все 3D-расчеты изолированы в пуле воркеров, масштабируемых независимо от веб-трафика
    3. Быть отказоустойчивой и оптимизированной за счет внедрения кеширования и репликации
    4. UI MES более отзывчивой за счет оптимизации запросов дашборда

# TOP-3 инициатив на ближайшие 6 месяцев

    1. Внедрить мониторинг зависаний заказа. Останавливает отток клиентов и потерю контрактов. Компании жизненно необходимо видеть, где прямо сейчас застревают заказы, почему они не доходят до CRM/производства и автоматически возвращать упавшие сообщения из очередей.
    2. Вынос и оптимизация запросов дашборда MES. Разблокирует операторов. Позволяет им брать заказы без задержек.
    3. Репликация и кеширование баз данных. Позволит ускорить отзывчивость системы в целом(запросы с UI, запросы от партнеров)
