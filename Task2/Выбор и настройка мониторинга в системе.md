# Мотивация

Внедрение серверного и бизнес-мониторинга — это не просто инструмент для инженеров, а система защиты выручки и репутации компании. Инвестиции в мониторинг окупятся за счет решения следующих бизнес-задач:

    - Предотвращение потери контрактов: Прямо сейчас мы узнаем о невыполненных B2B-заказах от рассерженных партнеров спустя месяцы. Мониторинг позволит настроить автоматические уведомления на «зависшие» заказы (например, если статус не менялся более 24 часов). Команда сможет реагировать проактивно, до того как клиент решит уйти.
    - Гарантия выполнения обязательств (SLA): Измерение реального времени нахождения заказа на каждом этапе позволит понять, почему нарушается обещание доставить изделие за 3 недели. Мы точно увидим, где возникает затор: в расчетах IT-системы или на физическом производстве.
    - Разблокировка работы операторов: Отслеживание времени отклика дашборда MES покажет объективную картину деградации. Доказав проблему и решив её, мы устраним простои операторов. Они смогут обрабатывать больше заказов, что напрямую увеличит производительность цеха.
    - Экономное масштабирование: Вместо того чтобы «вслепую» покупать мощные серверы при жалобах на тормоза, мониторинг покажет, где именно не хватает ресурсов. Мы сможем масштабировать инфраструктуру точечно (например, только воркеры для 3D-расчетов), экономя бюджет на облачные сервисы.

# Выбор подхода к мониторингу

Для получения объемной картины мы применим гибридный подход. Система состоит как из сервисов, обрабатывающих запросы, так и из инфраструктурных компонентов (очереди, базы данных). Поэтому для разных слоев мы будем использовать разные методологии: RED для уровня приложений и USE для уровня инфраструктуры.

1.  Подход RED (Rate, Errors, Duration). Применяем в слой приложений (Web-сервисы Магазина, CRM, MES) и публичный B2B API. Этот подход идеально подходит для синхронных сервисов, где важен клиентский опыт и скорость ответа.
    - Rate (Интенсивность): Количество запросов в секунду (RPS). Позволит увидеть реальную нагрузку от B2B-партнеров через API и пики активности в CRM/Магазине.
    - Errors (Ошибки): Количество неудачных запросов (HTTP 5xx, 4xx). Критично для отслеживания ошибок валидации 3D-моделей или падений бекенда MES при расчетах.
    - Duration (Продолжительность): Время ответа сервиса. Главная метрика для решения проблемы операторов — мы сможем отслеживать 95-й и 99-й перцентили (p95, p99) времени загрузки дашборда MES.

2.  Подход USE (Utilization, Saturation, Errors). Применяем в инфраструктурном слое (Брокер сообщений RabbitMQ, Базы данных в Yandex Cloud, инстансы EC2). Методология сфокусирована на внутренних ресурсах системы и поможет выявить «узкие горлышки» (bottlenecks) до того, как они уронят приложение.
    - Utilization (Утилизация): Нагрузка на CPU и использование оперативной памяти на серверах MES в моменты парсинга тяжелых 3D-моделей, а также I/O дисков баз данных.
    - Saturation (Насыщение): Индикатор очереди. Для нас это самая важная метрика: длина очередей в RabbitMQ, исчерпание пула соединений (Connection Pool) с БД и троттлинг на балансировщике.
    - Errors (Ошибки): Инфраструктурные сбои. Например, сообщения, попавшие в Dead Letter Queue (DLQ) в RabbitMQ, разорванные сетевые соединения, таймауты баз данных.

# Список возможных метрик для отслеживания

1. Number of `dead-letter-exchange` letters in RabbitMQ - необходимо отслеживать, чтобы выявлять потерянные заказы
2. Number of `message in flight` in RabbitMQ - отслеживание позволит оперативно реагировать на загруженность очереди и принимать меры по увеличению мощности
3. Number of requests (RPS) for shop / CRM / MES API - покажет реальную нагрузку на API, и поможет принять решение о необъости увеличения/уменьшения мощности ресурсов
4. Number of requests (RPS) per user for shop / CRM / MES API - поможет вычислить конкретного B2B-партнера, который заваливает запросами, чтобы включить для него Rate Limiting
5. CPU % for shop / CRM / MES API - метрика покажет, когда процессор загружен на 100% и блокирует другие процессы, сигнализируя о необходимости масштабирования или оптимизации
6. Response time (latency) for shop / CRM / MES API - позволит команде видеть объективную скорость загрузки данных и оценивать эффективность оптимизаций.
7. Number of HTTP 200 for shop / CRM / MES API - базовый показатель «здоровья» и доступности системы, необходим для расчета процента успешности (SLA/SLO)
8. Number of HTTP 500 for shop / CRM / MES API - триггер для немедленных алертов. Показывает, что код ломается (например, ошибка валидации кривой 3D-модели), помогая выявлять баги до репортов от QA или пользователей

# Ярлыки для метрик

1. ## Для метрик API (RPS, Latency, HTTP 200/500, Трафик):
   - `endpoint` или `path`: Конкретный путь запроса (например, `/api/orders`, `/api/calculate_3d`). Позволит найти самые медленные и тяжелые методы
   - `method`: HTTP-метод (GET, POST, PUT)
   - `client_type`: Тип клиента (b2b_api, b2c_web, crm_operator). Это критически важно, чтобы отделить розничных покупателей от наплыва запросов от партнеров.
   - `partner_id`: Идентификатор B2B-партнера (для метрики RPS per user). Поможет быстро найти того, кто DDOS-ит систему.
2. Для очередей RabbitMQ (Messages in flight, DLQ)
   - `queue_name`: Имя очереди (например, order_creation_q, 3d_calc_q).
   - `routing_key`: Ключ маршрутизации. Позволит понять, сообщения какого типа застревают или падают в мертвую очередь чаще всего.
3. Для инфраструктуры (CPU, Memory):
   - `instance_id` или `host`: Идентификатор конкретного сервера/пода. Поможет выявить проблему, если «железо» деградирует только на одной ноде из балансировщика.
   - `environment`: Среда (prod, release, dev).

# Какие метрики стоит добавить дополнительно?

1. Мониторинг бизнес-логики
   - Order counts per status: Количество заказов в каждом статусе (INITIATED, PRICE_CALCULATED, MANUFACTURING_APPROVED и т.д.)
   - Time in status: Ключевая метрика для решения проблемы жалоб. Позволит настроить алерт: «Если заказ висит в статусе X дольше 72 часов — отправить уведомление менеджеру».
2. Мониторинг баз данных
   - Slow queries rate: Количество SQL-запросов, выполняющихся дольше заданного порога (например, > 1 секунды). Эта метрика поможет разработчикам поймать конкретные неоптимизированные запросы

# План действий

Для реализации стратегии мониторинга необходимо выполнить следующие шаги. В качестве основного стека предлагается использовать стандартный и проверенный набор: Prometheus (Time-series база данных) и Grafana (Система визуализации).

1. Развертывание базовой инфраструктуры мониторинга
   - Развернуть инстанс Time-Series базы данных Prometheus для поллинга и хранения метрик.
   - Развернуть сервер Grafana и подключить Prometheus в качестве источника данных (Data Source).
   - Развернуть Alertmanager для маршрутизации и группировки уведомлений.
   - Обеспечить сетевую доступность: настроить правила Firewall/Security Groups так, чтобы Prometheus имел доступ к /metrics эндпоинтам всех сервисов и баз данных.
2. Сбор инфраструктурных метрик (USE-подход)
   - Установить Node Exporter на все EC2-инстансы для сбора системных метрик (CPU, Memory, Disk I/O, Network).
   - Включить встроенный плагин rabbitmq_prometheus в кластере RabbitMQ для сбора метрик очередей (Messages in flight, DLQ).
   - Настроить сбор метрик баз данных из Yandex Cloud (через интеграцию Yandex Cloud Monitoring с Prometheus или установку специфичного DB Exporter, например, postgres_exporter), чтобы получать данные по Connection Pool, Memory и размеру БД.
3. Инструментирование сервисов на уровне кода (RED-подход)
   - Включить и настроить отдачу метрик Для Online Shop и CRM (Java Spring Boot)
   - Настроить Middleware для автоматического сбора RED-метрик для всех HTTP-запросов.
   - Внедрение бизнес-метрик в код CRM и MES
   - Визуализация в Grafana (Разработка дашбордов)
   - Настройка системы оповещений (Alerting)

# Показатели насыщенности

1. Глубина очереди RabbitMQ. Пороговое значение `Queue Depth > 15 сообщений` (держится дольше 10 минут). Если в системе будет 5 воркеров, при среднем времени расчета обной модели 10минут, то при попадаении в очередь 16 сообщения, пользователь будет жадить более 30 минут. Действия при превышении порога:
   - Автоматическое масштабирование(запуск дополнительных EC2-инстансов с воркерами)
   - Активация Backpressure на API(автоматически начинает возвращать B2B-партнерам статус HTTP 429 Too Many Requests)
   - Алерт инженерам(контроль успешного запуска доп инстансов)
2. Исчерпание пула подключений к БД. Пороговое значение `Active Connections > 85%` от максимального размера пула (держится дольше 1 минуты)
   - Немедленное уведомление дежурному DevOps-инженеру или DBA
   - Заведение тикета: Автоматически создается тикет в Jira с приоритетом Blocker и прикрепленным трейсом текущих долгих SQL-запросов
3. Исчерпание рабочих потоков веб-сервера. Пороговое значение `HTTP Pending Requests / Surge Queue > 20` (запросы, ожидающие свободного потока обработки)
   - Балансировщик нагрузки перестает направлять трафик на этот конкретный инстанс
   - Отправка уведомления дежурному инженеру для анализа
